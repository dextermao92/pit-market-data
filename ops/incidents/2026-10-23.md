## Impact

- **Option snapshots: no slot lost, but late.** The 10:35 slot failed, its retry succeeded at 10:42:17
  (7 min late), and the next four slots started 3.5–5.5 min late until 11:00, when the schedule caught up.
- **Index snapshots: the 10:35 slot was lost.** Both attempts (10:35:01 and 10:38:02) hit the 2-min task
  timeout; the 10:40 slot ran at 10:45:29.
- Equity bars (Alpaca) were not affected.
- Late snapshots are still valid point-in-time data: each row is stamped with its real `ingested_at`.

During the stall, the Gateway logged no data-farm errors and quotes kept flowing before and after it.

## Root cause

**IBKR's contract-definition (secdef) server stopped answering for about 5 minutes.** At the time, every run asked
it for the underlying contract (`qualifyContracts`) and the listed expirations (`reqSecDefOptParams`) before any quote
request, once per chain. The option and index tasks used separate API connections but stalled at the same time.
What they had in common was these contract-definition requests, not market data. So one slow upstream service held up
a run whose actual job, streaming quotes, didn't need it.

## Contributing factors

- `RequestTimeout = 300 s` (sized for cold contract-detail downloads) let one hung request use the whole 6-min run budget.
- Retrying a failed run pushes the following slots back while `max_active_runs=1`.
- The RTH coverage metric bins runs by `started_at`. It counted the late 10:35 retry (started 10:42) as the
  10:40 slot and reported the 10:35 slot as missing (77/78), although that snapshot exists.

| Coverage metric: count a run toward the slot in its `run_id`, not its start time | — | Open |

## Lessons

- Look at what a run actually depends on. The pipeline only needed quotes, but it depended on a second IBKR service
  that it could just as well have asked once a day.
- A timeout sized for the slowest legitimate request (a cold download) is too long for a request that is normally instant.
