## Root cause

**The morning `contract_cache` refresh overloaded IBKR's contract-definition (secdef) service, and the Gateway then
froze.** Re-listing every expiry pulled ~24 MB in ~23k messages. About 7 minutes in, the data farms broke and
contract-definition requests stopped being answered. By 09:16 the Gateway no longer accepted API connections at all,
and IBC could not restart it.

Evidence:

- The size of the refresh (23.7 MB / 23,376 messages in attempt 1) and the timing: the breakage started during it.
- The same refresh stalled the secdef service about five minutes in **every morning from 10-28 to 11-02**, with or
  without IBKR's ~08:15 server reconnect, and stopped once the refresh was made small and paced (`b927d63`).
- The 08:15:42 `1100` / `1102` was a reconnect of the same session ("data maintained"), so it was not a second login.

**Ruled out: a second machine logging in with the same IBKR username.** The user was setting up a Windows desktop
that weekend, and the 1100 happened at 23:15 their time, the planned switch-over deadline. But a competing login ends
the old session. Here the session survived (`1102`), there was no re-login or "existing session" dialog in the Mac
Gateway log, and the failure recurred on later days with one machine.

## Contributing factors (why nothing recovered on its own)

1. **The self-healing path had a hole:** `check_gateway` only caught connect errors. A request that hung after
   connecting raised past `gateway_with_healing`, so the 09:02 check never sent RECONNECTDATA or RESTART.
2. **Only the 09:02 check could heal.** Once the collectors failed, nothing during the session tried to heal.
3. **IBC's RESTART can't fix a wedged Gateway.** Only a container restart could, and that needs a full login with phone 2FA.
4. **The person who could approve 2FA was asleep.** Every card went out between 23:33 and 08:30 AEDT.

## Lessons

- A cache refresh can also be a load test against someone else's service. Make it incremental and paced.
- Test the self-healing code against the failures that actually happen. "Connects but never answers" is not the
  same as "can't connect".
- Before trusting a recovery step, check it can run in the state that needs it. IBC's RESTART needs a working
  Gateway UI, which is exactly what was broken here.
- Write down the tempting explanation and the evidence that rules it out (the second machine). It is the first
  thing anyone will suggest next time.
